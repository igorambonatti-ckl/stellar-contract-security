Soroban contract audit · AI-assisted fuzzing

Two fuzzing arms, one contract, seven planted bugs.

AI proposes, the human curates, the fuzzer disposes. A model reads an expression and enumerates how it can go wrong. It cannot tell you whether that state is reachable — and it will state the unreachable case with more confidence than the real one. Execution is the only authority in the loop that cannot be argued into a false positive.

Evidence

Detection matrix

Both arms run the same engine over the same contract with the same budget. The only difference is the oracle: one asks did the call abort?, the other reads state back and compares it against an independently computed expectation. Reported per seed, never as an aggregate — one seed trips four distinct tests and would inflate the total on its own.

Why the gap exists

Six of seven bugs are silent

The baseline catches exactly the one bug that makes the contract abort. The rest accept the call, return normally, and leave the state wrong — shares duplicated, supply inflated by a wrapped multiplication, an entry left to be archived, the admin overwritten. A liveness oracle is structurally blind to all of it.

  • The AI's contribution was the oracle, not the harness. 16 of its 17 compile errors came from one wrong assumption about the SDK — caught by the compiler in seconds, costing nothing. What it contributed was knowing what to assert: 13 usable invariants from 16 proposals, including 10 of the 12 in a catalogue it never saw.

  • Both Soroban-specific invariants were derived from source alone — TTL management and the rule that authority must never be read from a tier that can silently expire. These are the properties with no EVM analogue.

  • Two independent instruments agree. Mutation testing knows nothing about the planted bugs; it mutilates the contract on its own. 1/7 and 34% for the baseline, 7/7 and 98% for the AI arm — which is what answers the objection a purpose-built benchmark cannot answer for itself.

Findings

What the process actually caught

Including the ones that were wrong. Each measurement error below produced a plausible number that survived until something contradicted it — and the list of what caught them is the argument for the method.

› REFUTED The AI's highest-confidence claim was false F-01

The input-prioritisation round identified, as “the highest-value truncation target in the file”, that withdraw can burn shares and pay zero. The reasoning was specific, cited the right lines, and was stated with more confidence than anything else it produced.

It is unreachable. assets ≥ total_shares holds over every reachable state, provable by induction over the four mutators — and with that, the payout is never zero. The model analysed one expression locally and never asked which states are reachable.

Outcome

The reason it is false became invariant N2, now asserted on every run. A refuted hypothesis turned into a kept invariant.

› FALSE POSITIVE A real accounting flaw that is not reportable F-02

The fuzzer broke the clean contract: deposit(from = vault) mints shares against a token transfer from the vault to itself, which leaves its balance unchanged. Value created from nothing. 

I3 violated by deposit: A1*T0=1000000000000000000 < A0*T1=1000000066000000000
                        (A0=1000000000 T0=1000000000 A1=1000000000 T1=1000000066)

The asymmetry is real. It is also unreachable on-chain: no external caller can forge the contract's own authorization. The path existed only because the harness mocked all authorization — a false red manufactured by the harness itself.

Outcome

Contract addresses stay in the pool as counterparties, where stranded value is a genuine hazard, and leave the caller position, where they cannot sign. Every detection from that run was discarded.

› TOOLING A flag that was accepted and silently ignored F-03

cargo fuzz --features is accepted by cargo-fuzz 0.13.2, never forwarded to the underlying build, and reports no error. The first matrix therefore announced that the AI arm had missed a bug — when that bug had never been compiled in.

The number was quiet, plausible, and pointed the wrong way. It was caught only because it contradicted the result from a different layer.

Outcome

The runner now verifies the feature set cargo actually resolved, and aborts if it is not what was asked for. Two weaker checks were tried first and both produced false alarms of their own.

› METHOD The assisted arm was briefly worse than the control F-04

The first coverage-guided AI target found 2 of 7 — and lost one the crude baseline caught. Not an oracle problem: operands came straight from the fuzzer's bytes, so it could never build multi-call state, and every call was wrapped in a fallible variant and checked only on success, so an operation that wrongly aborted was tolerated.

The fix was implementing the third prompt — which had been written, executed, committed verbatim, and never opened. 2/7 → 7/7.

Outcome

A prompt that is authored, executed and committed but never integrated produces no value and leaves no trace of its absence. Its generic half is now a reusable crate.

› SOROBAN Rent counters work as a TTL oracle; disk counters do not F-05

An invocation that wrote persistent state and bumped no rent has left an entry nothing is paying to keep alive. That oracle needs no knowledge of the contract's storage layout — making it the only TTL check here that applies to a contract you have not read, which is the situation an auditor is in.

The companion idea does not survive. “A disk read means an archived entry was restored” ignores that the counter also includes non-Soroban entries such as classic account balances, so any contract calling a token reads from disk while perfectly healthy. Written as an assertion, it failed on the clean build in under 90 seconds.

Outcome

Kept as a documented negative result rather than deleted. “Do the resource counters make a good TTL oracle?” is too coarse a question to have one answer.

› ECOSYSTEM EVM bug taxonomies do not port to Soroban F-06

overflow-checks is on in the Soroban project template, so naive arithmetic aborts rather than wraps. The classic integer-overflow bug barely exists here and had to be planted with an explicit wrapping multiplication to exist at all.

Conversely, the two bug classes with no EVM analogue — TTL mismanagement and authority read from a tier that can silently expire — are absent from every EVM-derived checklist, and are where the real Soroban risk sits.

Honesty

What this does not show

These bound what the numbers above are allowed to mean.

  • Not a productivity measurement. Both arms were authored by the assistant, so wall-clock compares one model to itself. The claim this cannot make is “AI makes a developer faster”.

  • Not a statistical result. One contract, one model, one run per arm. No variance estimate, no significance claim.

  • Not free of benchmark bias. The contract was purpose-built around the invariant catalogue, so a model reading it reads a contract whose shape already implies most of the properties.

  • Two access-control properties are asserted weaker than stated. “Only the incumbent authorized” is tested as “nobody authorized”, so a contract accepting any signer would pass. Flagged by the model in its own harness.
